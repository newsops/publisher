## Rule Anchor

- `.agents/rules/spec-workflow.md` — "Spec-Code Conformance Verification"
- `.agents/rules/spec-workflow.md` — "ABSOLUTE RULE: 검증은 스펙을 코드에 맞게 수정하지 않는다"

## 사용 시점

아래 경우 **필수**로 사용합니다:

- `specs/*.md` 기능 스펙이 생성되거나 수정된 경우
- `packages/*/docs/SPEC.md` 패키지 스펙이 생성되거나 수정된 경우
- 계약 테스트 파일이 생성되거나 수정되어 예상 동작이 변경된 경우

**트리거 조건:** 현재 변경셋에 스펙 문서 diff가 있는 경우.

## 핵심 원칙

**스펙이 진실의 원천.** 이 워크플로는 스펙에 맞게 코드만 수정합니다. 스펙 자체는 수정하지 않습니다. 스펙이 틀린 것으로 보이면 별도 워크플로(`spec-writing-standard`, `spec-first-development`)에서 처리합니다. 이 워크플로 내에서 스펙은 정확한 것으로 간주하고 코드가 준수해야 합니다.

## Workflow

```
Step 1: 영향받는 스펙 수집
         ↓
Step 2: 스펙 읽기 → 코드 읽기 → 각 단언 비교
         ↓
Step 3: 모든 격차 나열
         ↓
      격차 = 0?
      YES → Step 6: 회귀 테스트
      NO  ↓
Step 4: 스펙에 맞게 코드 수정 + 계약 테스트 추가
         ↓
Step 5: 빌드 + 테스트
         ↓
      → Step 2로 돌아가기 (반복)
```

### Step 1: 영향받는 스펙 수집

현재 작업에서 변경된 모든 스펙 파일을 식별합니다. 각 스펙에 대해 메모합니다:

- 파일 경로
- 이 스펙을 준수해야 하는 코드 패키지/파일
- 기존 계약 테스트 파일 (있는 경우)

### Step 2: 스펙 읽기, 코드와 비교

각 스펙 단언(엔드포인트, 타입, 에러 코드, 응답 형태, 상태 코드, 클래스 계약)에 대해:

1. 스펙 문장을 읽습니다
2. 해당 구현 코드를 찾습니다
3. 코드가 스펙과 정확히 일치하는지 확인합니다

주의 사항:

- HTTP 상태 코드 (스펙은 404, 코드는 400?)
- 응답 envelope 형태 (raw error vs 표준 형식?)
- 타입 이름과 필드 이름
- 에러 코드와 매핑
- 공개 API surface (스펙에 나열된 export가 모두 존재하는지?)

### Step 3: 모든 격차 나열

격차 표를 만듭니다:

| #   | 스펙 파일 | 스펙 단언 | 코드 위치 | 불일치 내용 |
| --- | --------- | --------- | --------- | ----------- |

격차가 없으면 Step 6으로 건너뜁니다.

### Step 4: 스펙에 맞게 코드 수정

각 격차에 대해:

1. 스펙을 준수하도록 구현 코드를 수정합니다
2. 수정된 동작을 검증하는 계약 테스트를 추가하거나 업데이트합니다

테스트는 수정 전 실패하고 수정 후 통과해야 합니다.

**이 단계에서 스펙을 수정하지 않습니다.** 스펙이 틀렸다고 생각되면 사용자에게 플래그하되, 현재 스펙에 맞게 코드를 수정합니다.

### Step 5: 빌드 및 테스트

```bash
# 영향받는 패키지 빌드
pnpm run build

# 또는 특정 패키지만
pnpm --filter @publisher/site build
pnpm --filter @publisher/content build
pnpm --filter @publisher/admin build

# 테스트 실행
pnpm run test

# TypeScript 타입 검사
pnpm run typecheck
```

모두 통과해야 합니다. 통과하지 않으면 수정 후 재시도.

그런 다음 **Step 2로 돌아갑니다**. 새로운 눈으로 스펙을 다시 읽고 코드와 비교합니다 (Step 4에서 수정된 코드가 새로운 격차를 드러낼 수 있음).

### Step 6: 회귀 테스트

Step 2에서 **격차가 0**일 때만 진행합니다:

```bash
# 전체 빌드 검증
pnpm run build

# 전체 테스트
pnpm run test

# TypeScript 타입 검사
pnpm run typecheck
```

모두 통과해야 준수 검증이 완료됩니다.

## 완료 기준

아래 **모두** 충족 시 검증이 완료됩니다:

- [ ] 모든 스펙 단언에 매칭되는 구현이 있음
- [ ] 모든 수정에 대응하는 계약 테스트가 있음
- [ ] 모든 계약 테스트가 통과
- [ ] 영향받는 모든 패키지가 에러 없이 빌드됨
- [ ] 타입 검사 에러 없음
- [ ] 전체 회귀 테스트 통과

## Anti-Patterns

- **스펙을 코드에 맞게 수정**: 이 워크플로는 스펙을 불변의 진실로 취급합니다. 스펙이 틀렸다면 플래그하되 여기서 변경하지 않습니다.
- **단일 패스 검증**: 스펙을 한 번 읽고 "이상 없음"을 선언하는 것. 격차는 연쇄적으로 발생 — 수정 후 항상 재검증합니다.
- **테스트 없이 코드 수정**: 모든 코드 수정에는 해당 계약 테스트가 있어야 합니다. 테스트 없는 수정은 회귀합니다.
- **회귀 건너뛰기**: 계약 테스트 통과는 필요조건이지 충분조건이 아닙니다. 회귀 테스트는 의도하지 않은 부작용을 잡습니다.

## Rule Anchor

- `.agents/rules/spec-workflow.md` — "Live Spec Policy"
- `.agents/rules/spec-workflow.md` — "Document Authority"

## 사용 시점

- **Mode A**: 기능 스펙(`specs/<feature>.md`) 또는 패키지 스펙(`packages/*/docs/SPEC.md`)을 새로 생성할 때
- **Mode B**: PR에서 동작, export, 타입, 계약이 변경되어 기존 스펙을 업데이트할 때
- **Mode C**: 스펙이 코드와 맞지 않아 드리프트를 복구할 때

---

## Mode A — 기능 스펙 초기 생성 (`specs/<feature>.md`)

새 기능, 페이지, API Route, 또는 주요 변경에 대한 설계 문서.

### 사전 조건

- `specs/_template.md`를 읽어 현재 템플릿 구조를 확인합니다.

### 필수 섹션

1. **개요**: 이 기능/변경의 목적과 배경 (1~2문장)
2. **목표**: 달성할 것 (체크리스트)
3. **비목표**: 이 스펙에서 다루지 않는 것
4. **설계**:
   - 데이터 모델: 콘텐츠 저장소/스냅샷 스키마 변경 (해당 시)
   - API 변경: 새로운 또는 수정되는 API Route (해당 시)
   - UI 변경: 영향받는 페이지/컴포넌트 (해당 시)
5. **테스트 계획**: User Execution Test Scenarios 포함
6. **마이그레이션**: 기존 데이터 영향이 있는 경우 (해당 시)

### 단계

1. `specs/_template.md`를 복사하여 `specs/<feature>.md` 생성
2. 모든 필수 섹션 작성
3. 관련 섹션만 포함 (해당 없는 섹션은 제거)

---

## Mode A — 패키지 스펙 초기 생성 (`packages/*/docs/SPEC.md`)

패키지의 공개 API 계약 문서.

### 사전 조건

- `packages/<name>/` 디렉토리가 존재합니다.
- 패키지 소스 코드를 충분히 읽어 아키텍처를 이해합니다.

### 필수 섹션 (9개 모두 필수)

| #   | 섹션                        | 목적                                                     |
| --- | --------------------------- | -------------------------------------------------------- |
| 1   | **Scope**                   | 패키지가 소유하는 것 (2~4문장)                           |
| 2   | **Boundaries**              | 패키지가 소유하지 않는 것과 그 책임이 어디에 있는지      |
| 3   | **Architecture Overview**   | 레이어 구조, 주요 컴포넌트, 사용된 디자인 패턴           |
| 4   | **Type Ownership**          | 이 패키지가 정의하는 SSOT 타입. 표: 타입 \| 위치 \| 목적 |
| 5   | **Public API Surface**      | export된 클래스, 함수, 타입. 표: Export \| Kind \| 설명  |
| 6   | **Extension Points**        | 소비자가 동작을 확장하는 방법                            |
| 7   | **Error Taxonomy**          | 에러 타입과 코드 (해당 시)                               |
| 8   | **Test Strategy**           | 현재 테스트 파일, 시나리오 검증, 커버리지 갭             |
| 9   | **Class Contract Registry** | 인터페이스 구현, 상속 체인                               |

### 단계

1. **현재 소스 읽기**: 디렉토리 구조, 주요 클래스, 인터페이스, export 파악
2. **9개 필수 섹션 작성**
3. **적용 가능한 선택 섹션 작성**: 플러그인/훅, 이벤트 아키텍처, 상태 생명주기, 설정
4. **일관성 검증**: 스펙에 참조된 모든 타입, export 기호, 에러 클래스가 소스에 존재하는지 확인

## Mode B — 점진적 업데이트

PR에서 패키지 동작, export, 타입, 계약이 변경될 때마다 사용. 구현 코드 작성 **전에** 스펙을 업데이트합니다.

이 모드는 수술적입니다: 변경에 영향받는 섹션만 수정합니다. 영향받지 않는 섹션은 재작성하지 않습니다.

### Step 1 — 영향받는 섹션 식별

| 이 PR에서 변경되는 것          | 업데이트할 섹션                  |
| ------------------------------ | -------------------------------- |
| 새 또는 제거된 공개 export     | Public API Surface               |
| 새 또는 변경된 타입/인터페이스 | Type Ownership                   |
| 새 또는 변경된 API Route       | API 변경 섹션                    |
| 새 또는 변경된 에러 타입/코드  | Error Taxonomy                   |
| 변경된 동작 의미론             | Architecture Overview, 관련 섹션 |
| 새 확장 포인트                 | Extension Points                 |
| 변경된 UI/페이지               | UI 변경 섹션                     |
| 데이터 모델 변경               | 데이터 모델 섹션                 |

### Step 2 — 현재 스펙 섹션 읽기

Step 1에서 식별된 섹션만 읽습니다. 영향받지 않는 섹션은 읽지 않습니다.

### Step 3 — 델타 작성

각 영향받는 섹션에 대해:

- **테이블의 새 행**: 행을 추가합니다. 기존 행의 번호나 형식을 변경하지 않습니다.
- **변경된 행**: 해당 행만 편집합니다.
- **제거된 export 또는 타입**: 행을 삭제합니다.
- **서술 단락**: 관련 문장이나 단락만 편집합니다. 섹션 전체를 재작성하지 않습니다.

### Step 4 — 일관성 확인

스펙에 추가하거나 변경한 모든 항목에 대해:

- 타입 이름이 소스에 존재하거나 같은 PR에서 생성되어야 합니다.
- Export 기호가 `index.ts`에 나타나거나 같은 PR에서 추가되어야 합니다.
- 에러 클래스가 에러 모듈에 존재하거나 같은 PR에서 추가되어야 합니다.

### Step 5 — 구현과 함께 스펙 업데이트 커밋

스펙 변경과 구현 변경은 같은 커밋 또는 같은 PR에 속합니다. 드리프트 복구를 제외하고 별도 PR로 분리하지 않습니다.

---

## Mode C — 드리프트 복구

여러 PR에 걸쳐 업데이트를 건너뛰어 드리프트가 누적된 SPEC.md에 사용.

1. **드리프트 열거**: 현재 SPEC 섹션을 실제 코드와 섹션별로 비교합니다.
2. **갭 나열**: 코드와 더 이상 일치하지 않는 스펙 단언, 그리고 스펙에 없는 코드 동작 표를 만듭니다.
3. **각 갭을 대상 점진적 업데이트로 해결**: Mode B Step 3 적용. 드리프트 복구는 현재 코드를 설명하도록 스펙을 수정합니다.
4. **일관성 확인 재실행**: Mode B Step 4까지 격차가 0이 될 때.
5. **전체 준수 검증 실행**: `pnpm run build && pnpm run test` (또는 특정 패키지 필터 사용).

드리프트 복구는 별도 PR입니다. 드리프트 복구와 기능 작업을 혼합하지 않습니다.

---

## Stop Conditions

- SPEC.md에 9개 필수 섹션 중 3개 미만 포함 (초기 생성 미완료).
- Type Ownership 테이블이 소스에 존재하지 않는 타입을 참조.
- Public API Surface가 `index.ts`에 없는 export를 나열.
- SPEC.md가 실제 코드 구조와 모순되는 아키텍처를 설명.
- 점진적 업데이트가 현재 변경에 영향받지 않는 섹션을 재작성 (범위 초과).

## Anti-Patterns

- SPEC.md를 일회성 아티팩트로 취급 — 스펙은 살아있으며 모든 변경과 함께 발전해야 합니다.
- 구현 후 스펙 소급 작성 — 항상 스펙을 먼저 업데이트합니다.
- 국소적인 변경에 전체 문서를 재작성 — 점진적 업데이트만.
- 현재 코드와 일치하지 않는 미래 지향적 아키텍처 작성.
